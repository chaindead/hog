# HLD — `hog`: переписывание `hulog` (Go) на Rust

Статус: **на апрув**. Дата: 2026-09-11. Rust 1.96.1, edition 2024, MSRV 1.87.

Всё, что помечено «проверено», проверено сборкой и запуском кода, а не только рассуждением.

## 1. Что делает исходный `hulog` и что в нём сломано

`hulog` — 200 строк Go: читает stdin построчно, строку не начинающуюся с `{` печатает как есть, иначе парсит JSON, рекурсивно уплощает вложенные объекты в точечные ключи (`grpc.time_ms`), исключает поля по полному точечному пути (исключение обрезает всё поддерево), печатает `<ts> [LVL] <msg> key=value...`.

Четыре дефекта, подтверждённые по исходникам:

1. **Поток молча обрывается.** `bufio.Scanner` с лимитом 1 MiB на строке длиннее лимита возвращает `ErrTooLong`, `Scan()` даёт `false`, цикл в `main.go:57` заканчивается, а `scanner.Err()` никто не проверяет. Одна длинная строка — и теряется **весь остаток лога**, процесс выходит с кодом 0.
2. **Кэш layout'а таймстампа никогда не срабатывает.** `helpers.go:26` вызывает `time.Parse(timeStr, layout)` — аргументы переставлены относительно `Parse(layout, value)`. Цикл по 7 layout'ам крутится на каждой строке вечно; а если бы быстрый путь когда-нибудь сработал, он напечатал бы время, выведенное из строки layout'а.
3. **Тихая потеря данных.** `{"empty":{}}` исчезает (`parser.go:65` рекурсирует в пустой объект и ничего не выдаёт). Значения не экранируются, поэтому `wide=a b c=d` нечитаемо машиной. `null` рендерится пустой строкой. Дубликаты ключей — молча побеждает последний.
4. **Производительность уже решена.** Go-бенчмарк из `main_test.go`: 804–2056 нс/строку. Замер Rust-прототипа: `serde_json` + `RawValue` — **303 нс/строку (403 MiB/s)**. Любая наивная реализация на Rust выигрывает; все идеи про SIMD/арены/rayon отклоняются по одному этому числу.

**Важно про список исключений пользователя.** `parser.go:73` проверяет точечный путь *до* рекурсии, поэтому `-e grpc` обрезает всё поддерево — это поведение сохраняется и закреплено как инвариант (§6, «Инварианты рендера»). Отдельный вопрос — не переписывать за пользователя его собственный список: в нём исключён лист `grpc.request.deadline`, а `grpc.request` оставлен, то есть остальные `grpc.request.*` сохраняются намеренно. Схлопывать эти 14 записей до одного `grpc` при переносе нельзя — это удалило бы данные, оставленные сознательно. Записи переносятся в стартовый конфиг дословно, но закомментированными (§10.5).

~1850 строк не-тестового кода, ни один файл больше ~190 строк.

### lib.rs + тонкий main.rs — не вкусовщина, а требование

Проверено сборкой обеих схем. Bin-only **дисквалифицирован**, а не просто хуже:

```
error[E0433]: cannot find module or crate `hog` in this scope
error: could not compile `hog` (bench "render") due to 1 previous error
error: could not compile `hog` (test "t")  due to 1 previous error
```

`benches/` **невозможен** без lib-таргета, а сравнение с Go-бенчмарком — часть обоснования переписывания. И самые ценные функции проекта чистые (`render`, `command::template::expand`, `command::validate`, `config::edit::append`); через бинарник их тестирование превращается в спавн процессов и парсинг stdout, через lib — в `assert_eq!`. Подстановка в шаблон и проверка аргументов несут весь периметр безопасности.

Цена lib — не файл, а расползание видимости. Политика: по умолчанию `pub(crate)`, `pub` только там, где реально зовёт тест или бенч; `publish = false`; в `lib.rs` — `//! Внутренний крейт бинарника hog. Не стабильное API.`

Соответствует правилу `proj-lib-main-split` из установленного скилла.

### Ошибки

Двухслойно, это удовлетворяет одновременно `err-thiserror-lib` и `err-anyhow-app`:

* `error.rs` — **`thiserror`-энум** ровно для тех доменных ошибок, которые отображаются в **различные exit-коды**: `ConfigParse`, `MissingCommand`, `BadArgument`, `TemplateArity`, `CommandNotFound`, `CommandExit(i32)`.
* Всё остальное — **`anyhow`** с `.context()` по пути.
* `main()` возвращает `ExitCode`; маппинг — `match` по типизированному энуму, а не цепочка `downcast` по `anyhow::Error`.

`anyhow` отдельно оправдан правилом `err-anyhow-app`; типизированный энум нужен потому, что exit-коды — часть контракта CLI, и выводить их из текста ошибки нельзя.

## 3. Формат конфигурации (TOML)

### Поиск файла

Первое совпадение выигрывает, слияния между файлами нет:

1. `--config <PATH>` — ошибка, если нет
2. `$HOG_CONFIG` — ошибка, если нет
3. `$XDG_CONFIG_HOME/hog/config.toml`, иначе `~/.config/hog/config.toml`
4. ничего не найдено → встроенные дефолты, молча

Слои: `дефолты < файл конфига < флаги CLI`.

**XDG побеждает и на macOS.** `~/Library/Application Support` — конвенция для GUI-приложений с reverse-DNS идентичностью. `hog` — dev-CLI, которому место в dotfiles рядом с `~/.config/gh`, и **тот же файл должен работать без изменений на Linux-хостах**, куда он ходит по ssh. Путь считается шестью строками std (`XDG_CONFIG_HOME` → `HOME/.config`); `dirs`/`directories` непригодны — они по политике мейнтейнера хардкодят macOS-путь.

**Никакого неявного `./hog.toml` и обхода вверх по дереву.** Конфиг задаёт команды, исполняемые по SSH; автоподхват из CWD делает `git clone && cd && hog -r prod api` вектором RCE. Проектный случай покрывается явным `--config ./hog.toml`.

### Файл

```toml
# ~/.config/hog/config.toml   —  `hog config path` печатает реально читаемый файл.
# Все ключи опциональны. Неизвестный ключ — предупреждение с номером строки, не ошибка.

# Поля, скрытые из вывода. Ключи — точечные JSON-пути после уплощения;
# исключение "grpc" обрезает всё поддерево.
#   `hog config exclude add <field>`   дописывает сюда (персистентно)
#   `hog -e <field>`         ДОБАВЛЯЕТ к этому списку на один запуск
#   `hog -E`                 сбрасывает этот список (остаётся только то, что дал -e)
#   `hog -E -e foo`          исключения ровно = ["foo"]
#
# Пример из практики — раскомментируйте нужное. Пути точечные, поэтому
# "grpc.request.deadline" прячет только deadline, а остальные grpc.request.*
# остаются видимыми; "grpc" спрятал бы всё поддерево целиком.
exclude = []
# exclude = [
#   "serviceName", "serviceVersion", "log_id", "x_forwarded_for", "trace_id",
#   "grpc.start_time", "grpc.time_ms", "grpc.code", "grpc.method", "grpc.service",
#   "grpc.request.deadline", "span.kind", "system", "logger",
# ]

# ------------------------------------------------------------------ command
# Команда, порождающая поток логов. Запускается БЕЗ локального шелла: строка
# разбирается в argv по правилам шелла, затем в слова подставляются позиционные
# аргументы hog. {0} — первый аргумент, {1} — второй, и так далее.
# Голая {} и {{...}} остаются литералами: find -exec {} \; и
# docker --format '{{.Names}}' проходят нетронутыми.
#
# -tt   даёт удалённой команде pty: без него на ТИХОМ контейнере docker logs -f
#       остаётся висеть на хосте после Ctrl-C (нет трафика — нет EPIPE).
# -o ServerAliveInterval=15  по умолчанию у ssh это 0, и отвал VPN вешает
#       hog навсегда без вывода и без ошибки.
# 2>&1 внутри кавычек отработает (его увидит удалённый шелл); снаружи кавычек
#       он станет литеральным аргументом.
# Ключа нет — работает встроенный `echo {@}`, и свежая установка сразу
# показывает, куда едут аргументы. Раскомментируйте или задайте своим
# `hog config command set "<шаблон>"`.
# command = "ssh -tt -o ServerAliveInterval=15 {0} 'docker logs -f --since 1h myapp-{1}-1'"

# Какие JSON-ключи несут три особые колонки. Список кандидатов: побеждает
# первый присутствующий в строке, отдельно для каждой строки.
[fields]
ts    = ["ts", "time", "timestamp", "@timestamp"]
level = ["level", "severity", "lvl"]
msg   = ["msg", "message"]

[output]
# strftime от jiff. Значение без '%' обязано быть одним из двух зарезервированных
# слов: "raw" (печатать таймстамп байт-в-байт) или "none" (убрать колонку).
time_format = "%H:%M:%S"
time_zone   = "local"    # "local" | "utc" | IANA, напр. "Europe/Moscow"
color       = "auto"     # "auto" | "always" | "never" (NO_COLOR уважается)
sort_keys   = true       # false = сохранять порядок ключей из JSON

# Палитра для имён ключей. Цвет ключа = FNV-1a(имя) % len(палитры), поэтому он
# стабилен: один и тот же ключ всегда одного цвета — в этом запуске, завтра и
# на другой машине. Меняете палитру — меняется раскладка целиком (это ожидаемо).
# key_colors = ["#ff3366", "#66cc66", "#ff9933", "#66ccff", "#cc99ff",
#               "#cc9966", "#669999", "#ff9999", "#99cc66", "#9999cc"]

# Сопоставление нестандартных уровней со известными (pino/bunyan шлют числа).
# [output.levels]
# "30" = "info"
# "50" = "error"

```

**Порядок в файле значим.** `command` и `exclude` — верхнеуровневые ключи, поэтому они обязаны стоять **до** первого заголовка таблицы: в TOML голый ключ после `[output]` принадлежит этой таблице, то есть `command` разобрался бы как `output.command`. Ровно эта ошибка была в первой редакции HLD; `hog` её теперь диагностирует сам — `warning: config.toml:4: unknown key \`output.command\``.

**Секций хостов и транспорта нет.** Всё, что отличает один хост от другого — алиас, порт, `ProxyJump`, `IdentityFile` — живёт в `~/.ssh/config`, где работает и для `ssh`, `scp`, `rsync`. Всё, что отличает один способ чтения логов от другого, живёт в строке `command`. Двух механизмов, пересказывающих CLI ssh, в конфиге hog нет.

### Ключевые решения по конфигу

* **Аргументы hog уходят в шаблон по позициям**, а сам шаблон — в argv без локального шелла. Хост, сервис, интервал — всё это просто позиционные аргументы, hog не приписывает им смысла. Требование «хост из конфига» выполняется без дублирования `~/.ssh/config`: конфиг hog отвечает за то, *чем читать логи*, а `~/.ssh/config` — за то, *как дойти до хоста*.
* **Синтаксис шаблона — позиционный, как у `format!("{0} {1}")`.** Раскрывается ~40 строками вручную, без зависимостей. Подставляются только `{N}` с цифрами; голая `{}` и `{{…}}` — литералы. Отклонены: `${1}` (путается с настоящей shell-подстановкой в той же строке), `{{1}}` (намекает на движок шаблонов), любой templating-крейт. Арность проверяется: шаблон с `{0}` и `{1}` требует ровно двух аргументов.
* **`command` необязателен.** Нет ключа — работает встроенный `echo {@}` (§5). Поэтому в модели это `Option<String>`: отличить «не задан» от «задан» нужно для таблицы режимов ввода.
* **`hog config -c "<шаблон>"`** записывает шаблон в конфиг, сохраняя комментарии. Шаблон **проверяется до записи** — разбор `shlex`, корректность плейсхолдеров, правило «`{@}` отдельным словом». Записать заведомо сломанный шаблон нельзя: иначе ошибка всплыла бы при следующем запуске, вдали от места, где её создали.
* **Неизвестные ключи — предупреждение с номером строки, не ошибка.** Это осознанное отступление от правила `serde-deny-unknown-fields` — см. §7.
* **Запись с сохранением комментариев** через `toml_edit::DocumentMut` (`ImDocument` в 0.25 устарел; `Document<S>` — неизменяемый корень со спанами, `DocumentMut` — редактируемый). Запись атомарна: canonicalize → временный файл рядом → fsync → rename.

## 5. Режим команды (`hog <арг> <арг> ...`)

**Решение: hog не собирает ssh-вызов сам, а запускает произвольную команду из конфига.** ssh — часть этой команды, а не встроенная в hog сущность. Утилита перестаёт быть ssh-специфичной: одинаково работают `ssh`, `kubectl logs`, локальный `docker logs`, `aws logs tail` или свой скрипт.

### Позиционные аргументы

Плейсхолдеры в шаблоне **позиционные**, по образцу `format!("{0} {1}")`:

```toml
command = "ssh -tt -o ServerAliveInterval=15 {0} 'docker logs -f --since 1h myapp-{1}-1'"
```

`hog prod api` → `{0}` = `prod`, `{1}` = `api`. Это ровно форма привычной bash-обёртки (`slog prod api`), только без самой обёртки.

**Голая `{}` остаётся литералом.** Подставляются только `{N}` с цифрами и `{@}`. Это не педантизм: `find -exec {} \;` и `docker --format '{{.Names}}'` — реальные команды, которые обязаны пройти нетронутыми. `{{0}}` даёт литеральную `{0}`, `{{@}}` — литеральную `{@}`.

**`{@}` — ОСТАВШИЕСЯ аргументы**, то есть те, что не забрали индексированные плейсхолдеры. Разворачивается в отдельные слова argv на своём месте; если оставшихся нет, слово просто исчезает (как шелловское `"$@"` при пустом списке).

Правило ровно одно: пусть `N` — наибольший использованный индекс. Тогда `{0}…{N}` забирают `args[0..=N]`, а `{@}` — это `args[N+1..]`. Индексированных плейсхолдеров нет → `{@}` забирает всё.

```toml
command = "ssh -tt {0} 'docker logs -f {@}'"
```
`hog prod api --tail 50` → `{0}` = `prod`, `{@}` = `api --tail 50`.

**Раскрытие зависит от того, чем `{@}` оказалось после `shlex::split`:**

* `{@}` — слово argv целиком (`echo {@}`): заменяется на N отдельных слов; при N = 0 слово исчезает из argv, как шелловское `"$@"` при пустом списке.
* `{@}` внутри слова, собранного из кавычек (`'docker logs -f {@}'` — shlex отдаёт **одно** слово `docker logs -f {@}`): оставшиеся склеиваются одним пробелом на своём месте, повторную разбивку делает удалённый шелл. При N = 0 остаётся пустая строка.

Второй случай — это флагманский пример выше, и «отдельным словом argv» в нём физически невозможно: слово уже собрано кавычками до подстановки.

Отвергается **склейка `{@}` с непробельным соседом внутри слова**: `myapp-{@}-1`, `--tail={@}`, `{0}{@}`. Несколько аргументов, слитых в один токен, не имеют осмысленного толкования, и любой выбранный ответ был бы сюрпризом. Второй `{@}` в шаблоне тоже отвергается: он продублировал бы тот же остаток, чего никто не делает намеренно.

**Две модели арности:**

| Шаблон | Требуется аргументов |
|---|---|
| `{0}`, `{1}` | ровно 2 — и меньше, и больше ошибка |
| `{@}` | любое число, включая ноль |
| `{0}` и `{@}` | не меньше 1, сверху не ограничено |

Фиксированная арность ловит опечатки — лишний аргумент почти всегда промах. Вариативная нужна там, где хвост заранее не известен: `{0}` держит хост, `{@}` пробрасывает что угодно дальше.

**Пропуски индексов отвергаются при загрузке конфига.** Шаблон `"x {0} {2}"` потребовал бы три аргумента, из которых второй не подставляется никуда — то есть у пользователя просят значение, которое никуда не поедет. Это почти всегда опечатка (`{2}` набрано вместо `{1}`), и молча её принять значит превратить опечатку в непонятное поведение. Использованные индексы обязаны образовывать непрерывный ряд от нуля:

```
error: config.toml:12: command uses {0} and {2} but never {1}

  Indexed placeholders must run from {0} without gaps.
  Did you mean {1}?
```

**Команда по умолчанию — `echo {@}`.** Если в конфиге нет ключа `command`, работает она: `hog a b c` печатает `a b c`. Смысл в том, что свежеустановленный `hog` сразу показывает, куда едут аргументы, а `--help` печатает этот шаблон наравне с пользовательским. Прежнее требование «нет шаблона → ошибка» этим **отменено**: шаблон есть всегда.

Узкий случай ошибки остаётся один: `hog` без аргументов на терминале, когда `command` в конфиге не задан явно — тогда печатается справка с выходом 2, а не запускается `echo` вхолостую.

### Запуск без локального шелла

Шаблон разбирается в argv через `shlex::split`, процесс порождается напрямую — **локального шелла нет**. Уровень шелла ровно один: удалённый, внутри кавычек `'docker logs …'`. Это то же число уровней, что и в отвергнутой схеме со сборкой ssh-вызова, то есть модель экранирования не усложнилась.

Следствие: `2>&1` внутри кавычек отработает (его увидит удалённый шелл), а снаружи кавычек станет литеральным аргументом. Это надо сказать в комментарии стартового конфига.

### Безопасность: белый список вместо квотирования

Квотировать подставляемые значения **нельзя**: hog не может знать, попадёт ли `{1}` в слово, которое удалённый шелл разберёт ещё раз (`'docker logs myapp-{1}-1'` — разберёт) или в голый аргумент (`-l app={1}` — нет). В первом случае кавычки нужны, во втором они станут литеральными и сломают команду. Задача неразрешима в общем виде.

Поэтому **валидация по белому списку** `[A-Za-z0-9._:/@-]`, плюс ограничение длины 256 байт. Список покрывает имена docker/k8s/systemd, `user@host` и `host:port`, и отсекает всё, чем можно сломать любой из уровней: пробел, кавычки, `;`, `|`, `&`, `$`, бэктик, `<`, `>`, `(`, `)`, `*`, `?`, `~`, `\`, перевод строки, ESC и прочие control-символы. В отвергнутой схеме белый список был отклонён из-за имён с `/` и `.` — они в него входят, возражение снято.

Проверка происходит **до** подстановки; отказ выглядит так:

```
error: argument 2 contains characters that are not allowed: "api; rm -rf /"

  Arguments are substituted into a shell command, so hog only accepts
  letters, digits and . _ - : / @

  Check what would run:  hog --dry-run prod api
```

### Чем платим

Два неочевидных флага больше не подставляются кодом — они живут в шаблоне стартового конфига с комментариями:

* `-o ServerAliveInterval=15` — проверено, `ssh -G` показывает `serveraliveinterval 0` по умолчанию, поэтому без него отвал VPN вешает hog навсегда без вывода и без ошибки.
* `-tt` — без pty на **тихом** контейнере ssh не замечает разрыва (нет трафика → нет EPIPE), и `docker logs -f` остаётся работать на удалённом хосте после каждого выхода.

Знание не потеряно, но стало редактируемым, то есть его можно случайно стереть. Это осознанная цена за «что написано, то и запускается»; README обязан объяснить оба флага.

Огрубляется и триаж кодов выхода: hog больше не различает «не достучались» (ssh 255) и код самой удалённой команды — сообщает честное «команда завершилась с кодом N». Громкая строка в stderr при ненулевом коде остаётся: `command exited with status 255 after 1423 lines`.

### Процесс и сигналы — без изменений

`Stdio::piped()` для stdout; stdin потомка удерживается открытым (`let _keep = child.stdin.take();` — `Child::wait()` документированно закрывает stdin перед ожиданием); stderr наследуется, чтобы запрос пароля и диагностика ssh были видны немедленно. `Drop`-guard убивает и пожинает потомка. SIGPIPE остаётся `SIG_IGN`, `BrokenPipe` ловится в единственном месте записи → kill потомка → выход 141.

**SIGINT отдельно не ловим**: потомок остаётся в группе процессов hog, Ctrl-C доходит до обоих — проверено на настоящем pty.

**SIGTERM ловим через `signal-hook`.** Без обработчика `kill -TERM <pid hog>` завершает процесс без раскрутки стека, `Drop` не отрабатывает, и потомок уходит к pid 1. Пишущий потомок умирает сам (читающий конец stdout закрыт → EPIPE), а **тихий живёт вечно** — то есть ровно «тихий контейнер» из аргумента за `-tt`, только утечка переехала на процесс наружу. Воспроизведено на release-сборке: `sleep 600` пережил `kill -TERM` с `ppid=1`.

Обработчик делает единственное: убивает и пожинает потомка, затем завершает hog с кодом 143. Сигнал по группе (`kill -TERM -<pgid>`, systemd, container runtime) работал и раньше — hog не зовёт `setpgid`.

### Первый запуск без конфига

```
$ hog prod api
prod api
```

Это дефолтный `echo {@}`. `hog --help` показывает его в блоке «Configured command» с пометкой, что он встроенный, и подсказывает `hog config init`.

## 6. ТЗ CLI

### Грамматика — проверена на собранном бинарнике

```rust
#[derive(Parser)]
#[command(name = "hog", version, disable_version_flag = true, args_conflicts_with_subcommands = true)]
pub struct Cli {
    #[command(subcommand)] pub command: Option<Cmd>,
    #[command(flatten)]    pub run: RunArgs,
    #[arg(long, global = true, env = "HOG_CONFIG", value_name = "PATH")]
    pub config: Option<PathBuf>,
    /// Тег релиза, которым собран бинарник, либо `dev`
    #[arg(short = 'v', short_alias = 'V', long, action = clap::ArgAction::Version)]
    pub version: (),
}

#[derive(Args)]
pub struct RunArgs {
    /// Подставляются в шаблон команды по позициям: {0}, {1}, ...
    /// Пусто → режим чтения stdin.
    #[arg(value_name = "ARGS")] pub args: Vec<String>,

    #[arg(short='e', long="exclude", value_name="FIELD", value_delimiter=',')] pub exclude: Vec<String>,
    #[arg(short='E', long="reset-exclude")] pub reset_exclude: bool,
    #[arg(long, value_enum, default_value_t = ColorChoiceArg::Auto)] pub color: ColorChoiceArg,
    #[arg(long)] pub dry_run: bool,
    #[arg(long, value_name="FIELD")] pub ts_field: Option<String>,
    #[arg(long, value_name="FMT")]   pub ts_format: Option<String>,
    #[arg(long, value_name="FIELD")] pub level_field: Option<String>,
    #[arg(long, value_name="FIELD")] pub msg_field: Option<String>,
    #[arg(long, value_name="TZ")]    pub timezone: Option<String>,
}

#[derive(Subcommand)]
pub enum Cmd {
    /// Посмотреть и поправить конфиг
    Config { #[command(subcommand)] action: Option<ConfigCmd> },
    #[command(hide = true)] Completions { shell: clap_complete::Shell },
}

#[derive(Subcommand)]
pub enum ConfigCmd {
    /// Напечатать путь конфига, который реально читается
    Path,
    /// Создать стартовый конфиг
    Init,
    /// Открыть конфиг в $EDITOR
    Edit,
    /// Список исключений
    Exclude { #[command(subcommand)] op: Option<ExcludeOp> },
    /// Шаблон команды
    Command { #[command(subcommand)] op: Option<CommandOp> },
}

#[derive(Subcommand)]
pub enum ExcludeOp {
    /// Добавить поля в список исключений
    Add { #[arg(required = true, value_delimiter = ',')] fields: Vec<String> },
    /// Убрать поля из списка исключений
    Rm  { #[arg(required = true, value_delimiter = ',')] fields: Vec<String> },
}

#[derive(Subcommand)]
pub enum CommandOp {
    /// Записать новый шаблон (проверяется до записи)
    Set { template: String },
}
```

Поверхность `hog config` целиком в субкомандах — так каждое действие видно в `hog config --help` со своим описанием:

| Вызов | Что делает |
|---|---|
| `hog config` | разрешённая конфигурация и путь, откуда взята |
| `hog config path` | только путь |
| `hog config init` | создать стартовый конфиг |
| `hog config edit` | открыть в `$EDITOR` |
| `hog config exclude` | показать текущий список |
| `hog config exclude add trace_id,log_id` | дописать, сохранив комментарии |
| `hog config exclude rm trace_id` | убрать |
| `hog config command` | показать текущий шаблон |
| `hog config command set "ssh {0} 'docker logs {@}'"` | записать, с валидацией до записи |

Это **заменяет** прежние флаги `-e`/`-d`/`-c`/`--init`/`--path` у `hog config`. Флаги `-e`/`-E` верхнего уровня (разовые исключения для одного запуска) остаются без изменений — это другое действие и другое место.

Проверено сборкой: вложенность не задевает грамматику верхнего уровня — `hog prod api`, `hog -- config`, `hog -- config path` и `hog -e a,b prod api` разбираются как раньше.

Флага `-r/--ssh` нет: позиционные аргументы сами включают режим команды. `--since`/`--tail` тоже нет — переменный хвост забирает `{@}`.

Проверенная таблица разбора (снята с собранного бинарника):

| Вызов | Результат |
|---|---|
| `hog` | `args=[]` → режим stdin |
| `hog prod api` | `args=["prod","api"]` → режим команды |
| `hog prod api 30m` | `args=["prod","api","30m"]` |
| `hog -e a,b` | `args=[] exclude=["a","b"]` |
| `hog -e a,b prod api` | `args=["prod","api"] exclude=["a","b"]` |
| `hog prod api -e x` | `args=["prod","api"] exclude=["x"]` — флаг после позиционных работает |
| `hog -E -e foo prod api` | `args=["prod","api"] exclude=["foo"] reset=true` |
| `hog --dry-run prod api` | `dry_run=true` |
| `hog config` | субкоманда |
| `hog config exclude add grpc.code` | субкоманда |
| `hog -- config` | `args=["config"]` — так передаётся аргумент с именем субкоманды |
| `hog -- config api` | `args=["config","api"]` |

Субкоманда выигрывает у первого позиционного аргумента, поэтому хост по имени `config` передаётся как `hog -- config`. Это единственная неоднозначность в грамматике, и она разрешается стандартным `--`.

Грамматика пересобрана и проверена после перехода на позиционные аргументы. Ушли `requires` в обе стороны (нет больше пары `--ssh`/`SERVICE`) и предупреждение про `num_args = 1..` — но само правило осталось в силе: `num_args` на `-e` снова начал бы съедать позиционные аргументы, так что ставить его нельзя.

### Динамический help: шаблон из конфига

`--help` показывает не только семантику позиционных аргументов, но и **реальную команду из конфига пользователя** — иначе по безымянному `[ARGS]...` невозможно понять, что печатать.

Блок печатается после стандартных секций:

```
Configured command (~/.config/hog/config.toml):
  ssh -tt -o ServerAliveInterval=15 {0} 'docker logs -f --since 1h myapp-{1}-1'

Takes 2 arguments:
  hog <ARG0> <ARG1>

Example:
  hog prod api
```

Если шаблона нет — вместо блока подсказка, что делать дальше:

```
No command configured — hog reads stdin only.
  Run `hog config init`, then add a `command` template.
```

Это заодно закрывает вопрос «поставил hog, а дальше что».

**Аргументы остаются безымянными** (`<ARG0>`, `<ARG1>`). Ключ вида `args = ["host", "service"]` для красивых имён в usage сознательно отклонён: он способен разойтись с шаблоном (два имени против `{2}` в команде), а значит потребует сверки и ещё одного текста ошибки — цена выше пользы, раз шаблон и так напечатан рядом.

**Реализация — предпроход по argv, и в нём есть ловушка.** Чтобы учесть `--config`, приходится разбирать аргументы дважды: сперва частично, ради пути к конфигу, потом по-настоящему, уже с готовым `after_help`. Частичный проход обязан идти с `disable_help_flag(true)` и `disable_version_flag(true)`:

```rust
let pre = Cli::command()
    .ignore_errors(true)
    .disable_help_flag(true)      // иначе --help перехватит разбор,
    .disable_version_flag(true)   // try_get_matches вернёт Err(DisplayHelp),
    .try_get_matches();           // и --config потеряется
let cfg = pre.ok().and_then(|m| m.get_one::<PathBuf>("config").cloned());
```

Без этих двух строк `hog --config other.toml --help` молча показывает шаблон из конфига по умолчанию — вывод неверный, но правдоподобный, поэтому на все ветки (`--config` на существующий файл, на отсутствующий, `HOG_CONFIG` из окружения, без конфига вовсе) нужен тест. Механизм проверен на прототипе.

### Режимы ввода

Режим выбирается **наличием позиционных аргументов**, а неоднозначный случай доразрешается проверкой, терминал ли stdin. Никакой другой магии нет.

| Аргументы | stdin | `command` в конфиге | Поведение |
|---|---|---|---|
| есть | любой | задан | запустить его, stdin не читать |
| есть | любой | не задан | запустить дефолтный `echo {@}` |
| нет | пайп или файл | любой | читать stdin |
| нет | терминал | задан | запустить его |
| нет | терминал | не задан | краткая справка, выход 2 |

Последняя строка — единственное место, где отсутствие `command` вообще заметно: запускать `echo` вхолостую бессмысленно, а человек, набравший голый `hog` в терминале, хочет справку. Различить «задан» и «не задан» просто: в модели конфига это `Option<String>`.

Две строки стоит проговорить отдельно:

* `hog < file.log` — stdin не терминал, значит режим чтения. Работает как ожидается.
* `hog` на голом терминале **не виснет вечно в ожидании ввода** — это классический баг наивной реализации.

Шаблон без плейсхолдеров — законный случай: `command = "kubectl logs -f -l app=api"` и просто `hog`.

### Инварианты рендера — переносятся из hulog без изменений

Три свойства вывода закреплены как контракт, а не как деталь реализации. Они проверяются golden-тестами (`tests/render_golden.rs`) и не могут измениться незаметно.

**1. Ключи в хвосте отсортированы по алфавиту.** Сортировка по полному точечному пути, `sort_unstable_by`. Один и тот же набор полей всегда даёт одинаковый порядок, поэтому две строки можно сравнивать глазами по колонкам, а вывод стабилен для `diff`. Отключается `sort_keys = false` — тогда сохраняется порядок из исходного JSON.

**2. Цвет ключа стабилен и зависит только от символов ключа.** `FNV-1a(имя ключа) % len(палитра)` — ни позиции в строке, ни соседних полей, ни порядка появления. Следствие, ради которого это и нужно: `trace_id` всегда одного цвета, и глаз цепляется за него в потоке строк без чтения текста. Хеш берётся от **полного точечного пути**, поэтому `grpc.code` и `code` — разные ключи и разные цвета. Алгоритм и палитра совпадают с hulog, то есть привычная раскраска не поедет.

**3. Исключение обрезает всё поддерево.** `exclude = ["grpc"]` убирает `grpc.code`, `grpc.time_ms`, `grpc.request.deadline` — всё, что под ним, на любой глубине. Реализуется проверкой точечного пути **до** рекурсии в узел: совпало — узел не разворачивается вообще.

Сопоставление идёт **по границам сегментов, а не по префиксу строки**:

| Правило | `grpc.code` | `grpc.request.deadline` | `grpcStatus` |
|---|---|---|---|
| `exclude = ["grpc"]` | скрыт | скрыт | **виден** |
| `exclude = ["grpc.request"]` | виден | скрыт | виден |
| `exclude = ["grpc.request.deadline"]` | виден | скрыт | виден |

Последняя колонка — важная: `grpcStatus` начинается с тех же букв, но это другой сегмент, и он остаётся. Ровно поэтому исключения задаются точечными путями, а не глобами или подстроками.

### Семантика `-e`

* повторяемый **и** через запятую: `-e a,b -e c` → `[a,b,c]`;
* `-e` **ДОБАВЛЯЕТ** к списку из конфига;
* `-E` / `--reset-exclude` — сбрасывает список из конфига;
* `-E` и `-e` **совместимы и осмысленны вместе** — это и есть способ переопределить список (требование №6).

| Вызов | Действующие исключения |
|---|---|
| `hog` | список из конфига |
| `hog -e foo` | список из конфига **+** `foo` |
| `hog -E` | пусто — показать всё |
| `hog -E -e foo` | ровно `["foo"]` |

`hog config exclude add <field>` дописывает в конфиг с сохранением комментариев, `hog config exclude rm <field>` убирает.

У `-E` **нет** `conflicts_with="exclude"` — иначе `-E -e foo` отвергалось бы. `exclude` — обычный `Vec<String>`, а не `Option<Vec<String>>`: при аддитивной семантике различать «не задан» и «задан пустым» не нужно.

### `-v` / `--version`

Печатает **тег, которым собран релиз**, а не только версию из `Cargo.toml`:

```
$ hog --version          # релизная сборка
hog v1.0.0

$ hog --version          # локальная сборка из рабочей копии
hog dev (a1b2c3d, dirty)
```

Источник — `build.rs`, минимальный и идемпотентный (`proj-build-rs-minimal`):

1. `$HOG_VERSION` — задаёт CI из тега;
2. иначе `git describe --tags --always --dirty`, если это git-копия и git доступен;
3. иначе `dev`.

Плюс `cargo:rerun-if-env-changed=HOG_VERSION` и `rerun-if-changed` на `.git/HEAD`, чтобы строка не залипала. Отсутствие git — не ошибка сборки: сборка из tarball обязана работать.

Короткий флаг — `-v`, как попросили, с `-V` как псевдонимом: `-V` у clap стандартный, и мышечная память на него у людей есть. Конфликта с «verbose» нет — такого флага в hog не планируется.

### Коды выхода

| Код | Значение |
|---|---|
| 0 | успех / входной поток закончился |
| 1 | ошибка времени выполнения (конфиг, шаблон, недопустимый аргумент) |
| 2 | ошибка использования (clap) |
| 127 | команда не найдена в PATH |
| 141 | наш stdout закрыт (`\| head`) |
| *n* | проброшен код запущенной команды |

### Переменные окружения

`NO_COLOR`, `CLICOLOR_FORCE`, `HOG_CONFIG`, `XDG_CONFIG_HOME`, `HOME`, `TERM`.

## 7. Сверка с установленным скиллом `rust-skills` (265 правил)

Совпадает: `proj-lib-main-split`, `proj-msrv-declare`, `err-anyhow-app` + `err-thiserror-lib` (двухслойно), `perf-io-buffering`, `test-snapshot-testing` (insta), `test-criterion-bench`, `test-integration-dir`, `test-cfg-test-module`, `opt-lto-release`, `opt-codegen-units`, `lint-deny-correctness`.

Три **осознанных отступления**, каждое из-за специфики проекта:

1. **`panic = "abort"` — НЕ ставим**, хотя `perf-release-profile` его рекомендует. `abort` отключает раскрутку стека, поэтому `Drop`-guard, убивающий потомка, никогда не отработает при панике → осиротевший `docker logs -f` на проде. Общий совет здесь проигрывает конкретному инварианту.
2. **`serde-deny-unknown-fields` — не применяем.** Рацио правила (опечатка `timout_secs` молча игнорируется) верное, но жёсткий отказ ломает совместимость вперёд: конфиг с ключом от более новой версии hog перестал бы работать на старой. Берём обе выгоды: не `deny_unknown_fields`, а явный аудит через спаны `toml_edit` с **предупреждением и номером строки**. Опечатки ловятся, совместимость вперёд сохраняется.
3. **`obs-tracing-over-log` — отклонено для v1.** Тащить фреймворк логирования в форматтер логов — расползание объёма. Несколько диагностик идут через `eprintln!` в stderr.

Правила, которые надо держать в голове при реализации (в hot path): `anti-format-hot-path` и `mem-write-over-format` — рендер обязан писать `write!` в переиспользуемый буфер, очищаемый на каждой строке, никаких `format!`; `mem-reuse-collections` — буферы уплощения переиспользуются между строками; `coll-map-choice` — для отсортированного вывода `Vec<(Cow<str>, Cow<str>)>` + `sort_unstable_by`, а не `BTreeMap` с аллокацией на узел; `api-parse-dont-validate` — валидирующий newtype `SafeArg` для позиционных аргументов, чтобы подстановка в шаблон физически не могла принять непроверенную строку.

## 8. Улучшения относительно Go

Принцип отбора (он и делает отказы защитимыми). Пункт попадает в v1, только если верно одно из трёх:
1. без него hulog **теряет или портит данные**;
2. этого требует заявленное требование;
3. он использует знание, которое есть **только у парсера** — порядок уровней, настроенные имена полей, действующий набор исключений, — и которое downstream-утилита восстановить не может.

Режется всё, что уже делает пайп (`grep`, `jq`, `head`), и всё, что раздваивает модель вывода.

### v1 — обязательный минимум надёжности

| Пункт | Цена |
|---|---|
| Побайтовое чтение строк `read_until(b'\n')` под `take()` 1 MiB; строки сверх лимита **выводятся** и дренируются до `\n` (никогда не теряются, память ограничена); невалидный UTF-8 проходит насквозь (`BufRead::lines()` **запрещён** — рвёт поток на первом плохом байте); один хвостовой `\r` снимается; финальная строка без `\n` рендерится | S |
| Broken pipe в единственном месте записи (см. §5) | S |
| **Политика flush**: `BufWriter` + `flush()`, когда `reader.buffer().is_empty()`. Нулевая задержка в follow-режиме, батчинг при редиректе, без флага и без tty-эвристики (`tail -f x \| hog` — и пайп, и live одновременно) | S |
| Корректность рендера: logfmt-квотирование значений с пробелами/`=`/кавычками; всегда экранировать `\n`, `\t` и ESC (заодно закрывает инъекцию escape в терминал); `{}`, `[]`, `null`, `""` рендерятся явно; задокументированная политика дубликатов ключей | S |
| Таймстампы: правильный порядок аргументов парсинга, работающий кэш layout'а, неразобранное печатается сырым; `time_zone = local` по умолчанию | S |
| Цвет: `--color`, `NO_COLOR`, `CLICOLOR_FORCE` + **даунгрейд truecolor→256** через `anstyle-lossy` | S |
| Жизненный цикл процесса: `Drop`-guard, таблица кодов выхода, громкая строка в stderr при ненулевом коде команды | S |

### v1 — заявленные требования

TOML-конфиг (M), модель исключений `-e` / `-E` (S), поверхность `hog config` субкомандами (S), режим команды с позиционным шаблоном и `{@}` (M), `--dry-run` (S), динамический help с шаблоном из конфига (S), `-v/--version` через `build.rs` (S).

Переменный интервал, ради которого задумывались `--since`/`--tail`, получается бесплатно: хвост забирает `{@}`, и `hog prod --since 30m` работает при шаблоне `ssh {0} 'docker logs -f {@}'`.

### Отклонено в v1 (и почему)

| Пункт | Почему |
|---|---|
| `-g/--grep <regex>` | переизобретает `grep`, теряет его флаги (`-v`, `-A/-B/-C`), тянет `regex` |
| `-i/--include` (allowlist) | весь рабочий процесс пользователя построен на исключениях (список из 14 записей); allowlist создаёт конфликт приоритетов |
| Глоб-исключения `grpc.*` | обрезка поддерева уже покрывает главный случай: `-e grpc` убирает всё вложенное (см. «Инварианты рендера»). Глоб добавил бы только шаблоны вида `*.deadline`, а рядом — риск: `grpc.*` в наивной реализации цепляет и `grpcStatus`. Механизм обрезки поддерева этим отказом **не затрагивается** |
| Многострочные значения блоками | ломает инвариант «одна запись — одна строка», от которого зависит `hog \| grep` и `hog \| head` |
| `-o/--output json` | скрывает нерешённую развилку: плоские точечные ключи или исходный вложенный объект |
| Автопереподключение | проблема дедупликации перечитанных строк не решается дёшево |
| SIMD/арены/rayon | 303 нс/строку уже в 3–6 раз быстрее Go; `anti-premature-optimize` |

### v2

`--level >=warn` (использует знание парсера — проходит критерий 3), спецобработка поля `error`/stacktrace, настраиваемая палитра, относительные таймстампы, несколько сервисов одновременно с префиксом строки.

## 10. Сборка и релиз

### Про goreleaser и «одну джобу»

**Кросс-компиляцию Rust поддерживает.** Разница с Go в линковке: у Go при `CGO_ENABLED=0` собственный линкер и все цели в тулчейне, Rust зовёт внешний. Проверено запуском: `cargo build --target` проходит фазу `Compiling` для любой цели и падает ровно на линковке (`linker \`link.exe\` not found`, `ld: unknown options: --as-needed`).

**Одной джобой через goreleaser собрать МОЖНО** — это проверено, а не выведено. Билдер `builds: - builder: rust` существует с goreleaser v2.5 (декабрь 2024), в OSS, дефолт `cargo zigbuild --target=<T> --release`. Агент собрал настоящий `hog` в Linux-контейнере под все 6 целей, включая обе `*-apple-darwin`, и запустил получившийся Mach-O на macOS — **без macOS SDK**, потому что zig везёт `libSystem.tbd`, а у `hog` нет ни одной C-зависимости.

Первая редакция этого раздела утверждала, что одна джоба невозможна из-за SDK. Это было неверно, и здесь зафиксировано, чтобы к вопросу не возвращаться.

**И всё же берём не его.** Причина не техническая, а эксплуатационная:

* билдер официально экспериментальный и печатает `you are using the experimental Rust builder` на каждом запуске (строка живёт в исходниках v2.18.1);
* в цепочку добавляются zig и cargo-zigbuild;
* `x86_64-pc-windows-msvc` через zigbuild **не собирается** — нужен отдельный `tool: cargo-xwin` либо понижение до `gnu`;
* в Rust-экосистеме так не делает **никто** из 13 изученных проектов, поэтому при поломке сверяться будет не с чем.

Одна джоба здесь экономит две джобы и стоит места, где ты единственный.

### Что делают другие (проверено чтением их release.yml)

| Подход | Проектов | Кто |
|---|---|---|
| Ручная матрица на нативных раннерах | **11 из 13** | ripgrep, fd, bat, hyperfine, zoxide, delta, helix, nushell, jj, starship, rust-analyzer |
| `cargo-dist` | 2 из 13 | uv, ruff — и оба лишь как оркестратор (`build-local-artifacts = false`), сборка вынесена в свои джобы ради PyPI-колёс |
| goreleaser | 0 из 13 | — |

`cross-rs` вызывается у 7 из 13 — и это наследие: все они написали свои файлы в 2018–2021 и не переписывали, последний релиз `cross` — v0.2.5 от 2023-02-04. Всё, написанное заново после августа 2025, берёт бесплатные нативные arm64-раннеры: jj, helix, rust-analyzer. Причина датируется точно — arm64-раннеры для публичных репозиториев стали общедоступны и бесплатны 2025-08-07.

### Решение

Ручная матрица из 6 целей на **трёх** метках раннеров, а шаг «собрать → упаковать → залить» отдан `taiki-e/upload-rust-binary-action` + `taiki-e/create-gh-release-action` — это даёт паритет с goreleaser без единой строки собственного bash. Образец: `ast-grep/ast-grep`.

| Цель | Раннер | Архив |
|---|---|---|
| `x86_64-unknown-linux-musl` | ubuntu | `hog_Linux_x86_64.tar.gz` |
| `aarch64-unknown-linux-musl` | ubuntu arm | `hog_Linux_arm64.tar.gz` |
| `x86_64-apple-darwin` | macos | `hog_Darwin_x86_64.tar.gz` |
| `aarch64-apple-darwin` | macos | `hog_Darwin_arm64.tar.gz` |
| `x86_64-pc-windows-msvc` | windows | `hog_Windows_x86_64.zip` |
| `aarch64-pc-windows-msvc` | windows | `hog_Windows_arm64.zip` |

Меток три, а не шесть: **обе darwin-цели собираются на одном macos-раннере** штатным Apple-тулчейном (так делают ripgrep и hyperfine), и **`aarch64-pc-windows-msvc` кросс-линкуется на обычном windows-раннере** (так делают zoxide и ast-grep).

**musl, а не gnu** — это и есть эквивалент `CGO_ENABLED=0`: статический бинарник идёт на любом дистрибутиве, тогда как `gnu` линкует glibc динамически и упадёт на системе старше раннера. Только musl в релизе держат ripgrep, zoxide и jj. Для musl на ubuntu нужна одна строка `apt-get install musl-tools`.

Имена архивов повторяют hulog: у `upload-rust-binary-action` вход `archive` принимает произвольную строку, а дефолты (`tar: unix`, `zip: windows`, бинарник в корне архива) совпадают с goreleaser.

### Два workflow

* **`ci.yml`** на push и PR: `cargo fmt --check`, `cargo clippy --all-targets -- -D warnings`, `cargo test`, отдельная джоба на MSRV 1.87 (`proj-msrv-declare` требует не только объявить, но и проверять).
* **`release.yml`** на тег: матрица выше, sha256 на каждый ассет (`checksum: sha256` — у этого входа нет значения по умолчанию, включать явно), GitHub Release с автогенерённым changelog. Релизная джоба экспортирует `HOG_VERSION` из тега, `build.rs` вшивает его в бинарник (§6). CI сверяет тег с версией в `Cargo.toml` до сборки.

Дёшево и стоит взять заодно: четыре строки `[package.metadata.binstall]` в `Cargo.toml` делают `cargo binstall hog` рабочим без отдельного инсталлятора — так поступают jj и nushell.

### Что останется непроверенным

Workflow нельзя выполнить локально. До первого пуша в `chaindead/hog` не проверены: реальные метки раннеров на момент запуска, поведение `upload-rust-binary-action` на конкретных именах архивов, сборка `aarch64-pc-windows-msvc` и обеих darwin-целей в кросс-режиме, и то, что `musl-tools` достаточно для линковки на arm-раннере. Это надо честно держать в голове при первом релизе, а не считать пайплайн проверенным.

## 11. Решённые вопросы

Открытых вопросов нет. Зафиксировано:

1. **Секции транспорта нет вообще.** hog не собирает ssh-вызов, а запускает произвольную команду из верхнеуровневого ключа `command`; ssh — часть этой строки. Ушли `[ssh.hosts.*]`, `options`, `pty`, `vars`, `{service}`/`{host}`/`{since}`/`{tail}` и флаг `-r/--ssh`. Утилита перестала быть ssh-специфичной.
2. **Аргументы позиционные.** `hog prod api` подставляет `prod` в `{0}`, `api` в `{1}`. Нет аргументов — режим чтения stdin, с доразрешением по `IsTerminal` (§6, «Режимы ввода»). Голая `{}` остаётся литералом, арность проверяется.
3. **Безопасность — белый список `[A-Za-z0-9._:/@-]`, не квотирование.** Квотировать нельзя: hog не знает, попадёт ли аргумент в слово, которое удалённый шелл разберёт ещё раз. Белый список безопасен на обоих уровнях и покрывает имена docker/k8s/systemd, `user@host`, `host:port`.
4. **`pty = true` и `ServerAliveInterval` переехали в шаблон** стартового конфига с комментариями, потому что кодом их больше не подставить. Знание сохранено, но стало стираемым — README обязан объяснить оба флага.
5. **`time_zone = "local"` по умолчанию.** Расходится с hulog: Go сохраняет офсет входной строки, поэтому для входа с `Z` hulog печатает UTC. **Требует абзаца в README про миграцию**; `time_zone = "utc"` возвращает прежние цифры.
6. **`-e` добавляет, `-E` сбрасывает.** `hog` → конфиг; `hog -e foo` → конфиг + `foo`; `hog -E` → пусто; `hog -E -e foo` → ровно `["foo"]`. Последняя форма и есть переопределение из требования №6. У `-E` **нет** `conflicts_with="exclude"`.
7. **`{@}` — ОСТАВШИЕСЯ аргументы**: при наибольшем использованном индексе `N` это `args[N+1..]`; индексированных плейсхолдеров нет → все. Отдельным словом целиком, второй `{@}` и склейка с непробельным соседом (`myapp-{@}-1`) отвергаются, индексы обязаны идти без пропусков от `{0}`. Дефолтная команда — `echo {@}`; требование «нет шаблона → ошибка» **отменено**, шаблон есть всегда. Узкий остаток — голый `hog` на терминале без явного `command` печатает справку, а не запускает `echo` вхолостую.
8. **Поверхность `hog config` — субкоманды**, не флаги: `path`, `init`, `edit`, `exclude add/rm`, `command set`. Заменяет исходное требование «`hog config -e <field>`». Шаблон в `command set` проверяется до записи.
9. **`-v`/`--version`** печатает тег релиза или `dev`; источник — `build.rs` по цепочке `$HOG_VERSION` → `git describe` → `dev`.
10. **`--dry-run`** печатает собранный argv и выходит, ничего не запуская.
11. **14 полей — закомментированными** в стартовом конфиге, с пояснением про точечные пути. Из коробки hog ничего не скрывает.

Блокеров не осталось, можно начинать с вехи v0.1.
